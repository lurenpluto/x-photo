# XPhoto 任务系统设计（可扩展版）

## 1. 目标

任务系统需要支持：

- 多种触发方式：手动触发、文件变更触发、定时触发、全库重扫触发
- 多种执行范式：扫描入库、识别处理（全库）、索引重建等
- 并行执行：可配置并发上限
- 中断后恢复：依赖持久化状态与检查点（checkpoint）继续执行

## 2. 触发模型

统一 trigger 类型：

- `manual`：用户主动触发
- `fs_watch`：文件系统监听触发
- `schedule`：定时任务触发
- `retry`：失败/取消后重试
- `full_reindex`：全库重扫或识别任务

## 3. 任务模型

### 3.1 通用任务表（预留）

`task_jobs`：用于承载未来多类任务（扫描、识别、索引等）

关键字段：

- `job_type`：任务类型
- `trigger_type`：触发来源
- `scan_job_id`：扫描任务关联（scan 类型）
- `status`：`pending/running/success/failed/cancelled`
- `payload_json`：任务输入参数
- `checkpoint_json`：任务检查点
- `progress_done/progress_total`：进度
- `retry_count/max_retries`：重试控制

### 3.2 扫描任务表

`scan_jobs` 作为扫描域任务表，当前已增强字段：

- `trigger_type`
- `cancel_requested`
- `processed_count`
- `resume_cursor_path`

## 4. 执行与并发控制

- 并发上限由 `scan.max_concurrent_jobs` 控制
- 服务内使用并发信号量（Semaphore）控制运行中的扫描任务数量
- 同一 source 同时仅允许一个 pending/running 任务，避免重复扫描冲突
- 任务调度器按 `scan.task_dispatch_interval_ms` 周期轮询 pending 任务

## 5. 中断恢复与检查点

### 5.1 状态持久化

扫描过程中的状态写入：

- `scan_jobs.processed_count`
- `scan_jobs.resume_cursor_path`
- `source_scan_states.last_scanned_path`

### 5.2 恢复策略

- `scan.resume_enabled = true` 时，任务启动会读取上次游标
- 按稳定排序（路径排序）恢复，从游标之后继续

### 5.3 检查点频率

- `scan.checkpoint_every` 控制每处理 N 条更新一次 checkpoint

## 6. 取消与重试

- 取消接口：`POST /rpc/v1/scan-jobs/{job_id}/cancel`
  - `pending`：立即置为 `cancelled`
  - `running`：置 `cancel_requested=1`，任务循环中安全中断
- 重试接口：`POST /rpc/v1/scan-jobs/{job_id}/retry`
  - 仅 `failed/cancelled` 可重试
  - 生成新任务，触发类型标记为 `retry`

## 6.1 文件变更触发入口

- 接口：`POST /rpc/v1/sources/{source_id}/scan:fs-watch`
- 请求体：`changed_paths`（本次检测到的变化路径）
- 行为：
  - 先把触发事件落入 `task_jobs`（`job_type=scan`，`trigger_type=fs_watch`）
  - 再投递扫描任务
  - 若已有同 source 的 fs_watch pending/running 任务，复用已有任务，避免风暴式重复触发

## 6.2 任务查询与控制接口

- `GET /rpc/v1/task-jobs`
  - 查询任务列表（可按类型和状态过滤）
- `GET /rpc/v1/task-jobs/{job_id}`
  - 查询任务详情
- `POST /rpc/v1/task-jobs/{job_id}/cancel`
  - 取消 pending/running 任务（若有关联 scan_job，会联动写入 `scan_jobs.cancel_requested` 或直接取消 pending scan）
- `POST /rpc/v1/task-jobs/{job_id}/retry`
  - 重试 failed/cancelled 任务，内部会增加 `retry_count`

## 7. 后续扩展建议

1. 抽象 `JobHandler` 接口，将扫描/识别/索引统一纳入任务引擎。
2. 引入任务优先级与队列调度策略（FIFO + priority）。
3. 将文件监听（fs_watch）事件接入任务投递层。
4. 引入分片任务（按 source/path 分片）提升并行吞吐。
