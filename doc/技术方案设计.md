# XPhoto V1 技术方案设计（架构 + 表结构 + RPC 草案）

## 1. 设计目标

基于《`doc/需求文档/需求文件.md`》落实可开发的 V1 技术方案，覆盖：

- 系统架构与模块边界
- 数据库模型与扩展策略
- 前后端交互 RPC 草案

V1 核心原则：**先可用、可扩展、可演进**。

## 2. 总体架构

### 2.1 架构分层

1. 存储抽象层（Storage Adapter）
2. 软件管理服务（Rust，核心业务层）
3. 前端展示层（Web）

```text
┌────────────────────────────────────────────────────┐
│                    Web Frontend                    │
│  照片流 / 相册 / 详情 / 批量操作 / 检索            │
└───────────────────────▲────────────────────────────┘
                        │ HTTP JSON RPC
┌───────────────────────┴────────────────────────────┐
│          XPhoto Service (Rust, 单进程可扩展)       │
│  API 层 / 扫描编排 / 元数据解析 / 相册服务 / 检索  │
│  任务队列 / 缩略图服务 / 权限与审计（预留）         │
└───────────────▲───────────────────▲────────────────┘
                │                   │
        Storage Adapter       Database Adapter
        (本地FS V1)           (SQLite V1, 可切PG)
```

### 2.2 V1 推荐技术选型

- 语言：Rust stable
- Web 框架：`axum`
- 异步运行时：`tokio`
- 数据库访问：`sqlx`（先 SQLite，后续可切 PostgreSQL）
- 元数据解析：`kamadak-exif`（EXIF）、`image`（基础信息）
- 哈希：`sha256`
- 序列化：`serde` + `serde_json`

说明：V1 默认 SQLite 可降低部署成本，后续通过 Repository/Adapter 层平滑切换 PostgreSQL。

配置系统（V1）：

- 使用本地配置文件：`service/config/config.toml`
- 支持 `--config <path>` 或 `CONFIG_PATH` 指定配置文件路径
- 环境变量可覆盖同名关键项（如 `BIND_ADDR`、`DATABASE_URL`、`LOG_DIR`、`LOG_LEVEL`）
- 相册目录规则支持配置化扩展（`album_rules.enabled`、`album_rules.date_delimiters`）
- 支持正则规则扩展（`album_rules.regex_patterns`，可配置 `regex/date_capture/name_capture/date_input_format`）
- 扫描并发支持配置（`scan.max_concurrent_jobs`）
- 扫描恢复支持配置（`scan.checkpoint_every`、`scan.resume_enabled`）
- 任务调度轮询间隔可配置（`scan.task_dispatch_interval_ms`）

## 3. 模块设计（Rust 服务）

### 3.1 目录建议

```text
service/
  src/
    api/               # RPC 路由与 DTO
    app/               # 应用装配与配置
    domain/
      photo/
      album/
      source/
      search/
    infra/
      storage/         # 文件系统适配器
      db/              # SQLx 仓储实现
      exif/            # 元数据解析
      thumb/           # 缩略图生成（可选）
    jobs/              # 扫描任务与增量任务
```

### 3.2 存储抽象接口

```rust
pub trait StorageAdapter {
    fn list_entries(&self, root: &str) -> Result<Vec<StorageEntry>, StorageError>;
    fn stat(&self, path: &str) -> Result<FileStat, StorageError>;
    fn open_read(&self, path: &str) -> Result<Box<dyn std::io::Read + Send>, StorageError>;
    fn remove_file(&self, path: &str) -> Result<(), StorageError>; // V1 可受配置保护
    fn canonical_id(&self, path: &str) -> Result<String, StorageError>; // 稳定唯一标识
}
```

V1 实现：`LocalFsAdapter`。后续新增 `DfsAdapter` 不影响业务层。

### 3.3 扫描处理流程

1. 读取 `source` 配置（多目录）
2. 遍历目录，按扩展名过滤图片（jpg/jpeg/png/heic/webp 等）
3. 计算文件签名与内容哈希：
   - `identity_key`（稳定身份键）：优先使用文件系统稳定标识（如 inode/file_id）
   - `content_hash`（内容哈希）：使用 `sha256(file_bytes)`
4. 提取 EXIF 与文件属性
5. 计算 `sort_time`：`shot_at > created_at > modified_at`
6. `upsert` 写入 `photo`
7. 根据目录规则尝试自动建相册并建立关联
8. 记录扫描任务结果（总数、新增、更新、失败）

### 3.4 自动建相册规则引擎（可扩展）

- 规则输入：目录名（最后一级或配置的层级）
- 内置 V1 默认规则：
  - `YYYY.MM.DD.<name...>`（点号分隔）
  - `YYYY_MM_DD_<name...>`（下划线分隔）
  - `YYYY-MM-DD-<name...>`（短横线分隔）
- 解析成功后得到：`album_date` 与 `album_name`
- 解析失败则跳过自动建相册
- 规则定义可配置化（正则 + 提取模板），便于后续扩充范式

## 4. 数据库设计

## 4.1 数据库选型与原则

- V1：SQLite（单机本地部署简单）
- 结构化主表 + 扩展 JSON 字段并存
- 常用查询字段必须建索引
- 多对多关系明确建中间表

### 4.2 表结构草案

> 字段类型为逻辑定义，实际类型按 SQLite/PostgreSQL 差异映射。

#### 4.2.1 `sources`（数据源）

- `id` TEXT PK
- `name` TEXT NOT NULL
- `root_path` TEXT NOT NULL UNIQUE
- `source_type` TEXT NOT NULL DEFAULT 'local_fs'
- `enabled` BOOLEAN NOT NULL DEFAULT true
- `created_at` DATETIME NOT NULL
- `updated_at` DATETIME NOT NULL

#### 4.2.2 `photos`（照片）

- `id` TEXT PK
- `source_id` TEXT NOT NULL FK -> sources.id
- `storage_file_id` TEXT NOT NULL
- `file_path` TEXT NOT NULL
- `file_name` TEXT NOT NULL
- `file_ext` TEXT
- `file_size` BIGINT NOT NULL
- `mime_type` TEXT
- `content_hash` TEXT
- `shot_at` DATETIME
- `created_at_fs` DATETIME
- `modified_at_fs` DATETIME
- `sort_time` DATETIME NOT NULL
- `width` INTEGER
- `height` INTEGER
- `exif_json` JSON/TEXT
- `gps_lat` REAL
- `gps_lng` REAL
- `remark` TEXT
- `deleted_at` DATETIME NULL
- `created_at` DATETIME NOT NULL
- `updated_at` DATETIME NOT NULL

约束建议：

- UNIQUE(`source_id`, `storage_file_id`)
- UNIQUE(`source_id`, `file_path`)

`photo.id` 生成与稳定性策略（关键）：

- `photo.id` 不使用 `content_hash` 生成，避免照片内容变更后主键变化。
- 推荐生成方式：`photo.id = sha256(source_id + ":" + storage_file_id)`。
- 其中 `storage_file_id` 来自存储适配层 `canonical_id()`，应尽量使用文件系统稳定标识（如 inode/file index）。
- 当照片发生编辑、重写、调色等内容变更时，仅更新 `content_hash` 与元数据，不变更 `photo.id`。
- 当底层无法提供稳定文件标识时，降级为 `source_id + normalized_path`，并在重命名/移动场景通过扫描合并策略修正关联。

#### 4.2.3 `albums`（相册）

- `id` TEXT PK（哈希 ID）
- `name` TEXT NOT NULL
- `remark` TEXT
- `cover_photo_id` TEXT NULL FK -> photos.id
- `auto_created` BOOLEAN NOT NULL DEFAULT false
- `album_date` DATE NULL
- `rule_key` TEXT NULL
- `created_at` DATETIME NOT NULL
- `updated_at` DATETIME NOT NULL

约束建议：

- CHECK(`name` <> '')

哈希 ID 方案：

- `album_id = sha256(normalized_name + album_date + random_salt)`
- 入库时做唯一约束冲突重试，确保不重复。

#### 4.2.4 `photo_albums`（照片-相册关系）

- `photo_id` TEXT NOT NULL FK -> photos.id
- `album_id` TEXT NOT NULL FK -> albums.id
- `seq_no` INTEGER NULL
- `created_at` DATETIME NOT NULL
- PK(`photo_id`, `album_id`)

#### 4.2.5 `scan_jobs`（扫描任务）

- `id` TEXT PK
- `source_id` TEXT NOT NULL
- `status` TEXT NOT NULL（pending/running/success/failed）
- `started_at` DATETIME
- `finished_at` DATETIME
- `total_count` INTEGER
- `new_count` INTEGER
- `updated_count` INTEGER
- `failed_count` INTEGER
- `error_message` TEXT

#### 4.2.6 `photo_features`（扩展特征，预留）

- `photo_id` TEXT PK FK -> photos.id
- `version` INTEGER NOT NULL
- `features_json` JSON/TEXT NOT NULL
- `updated_at` DATETIME NOT NULL

用于后续接入人物/事件/内容标签，不影响主表稳定性。

#### 4.2.7 `source_scan_states`（增量扫描状态）

- `source_id` TEXT PK FK -> sources.id
- `status` TEXT NOT NULL（idle/running/success/failed）
- `last_scan_started_at` DATETIME
- `last_scan_finished_at` DATETIME
- `last_scanned_path` TEXT
- `last_scanned_storage_file_id` TEXT
- `last_scanned_modified_at` DATETIME
- `last_scanned_content_hash` TEXT
- `last_error_message` TEXT
- `updated_at` DATETIME NOT NULL

用途：记录每个来源最近扫描进度与游标信息（最近扫描路径/文件标识），用于增量扫描与问题追踪。

#### 4.2.8 `task_jobs`（通用任务引擎，预留扩展）

- `id` TEXT PK
- `job_type` TEXT NOT NULL
- `trigger_type` TEXT NOT NULL
- `status` TEXT NOT NULL（pending/running/success/failed/cancelled）
- `payload_json` JSON/TEXT
- `checkpoint_json` JSON/TEXT
- `progress_done` INTEGER
- `progress_total` INTEGER
- `retry_count` INTEGER
- `max_retries` INTEGER
- `error_message` TEXT
- `run_after` DATETIME
- `started_at` DATETIME
- `finished_at` DATETIME
- `created_at` DATETIME NOT NULL
- `updated_at` DATETIME NOT NULL

用途：统一承载扫描、识别、索引重建等任务范式。

### 4.3 索引草案

- `idx_photos_sort_time` on `photos(sort_time desc)`
- `idx_photos_shot_at` on `photos(shot_at)`
- `idx_photos_file_name` on `photos(file_name)`
- `idx_photos_source_path` on `photos(source_id, file_path)`
- `idx_photo_albums_album` on `photo_albums(album_id, created_at desc)`
- `idx_albums_created_at` on `albums(created_at desc)`
- `idx_source_scan_states_status` on `source_scan_states(status, updated_at desc)`

## 5. RPC 草案（HTTP JSON 风格）

### 5.1 约定

- Base Path：`/rpc/v1`
- 认证：V1 可先留空（单机），接口层预留鉴权中间件
- 返回结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

### 5.2 Source 与扫描

- `POST /rpc/v1/sources`
  - 创建数据源：`{ name, root_path, source_type }`
- `GET /rpc/v1/sources`
  - 查询数据源列表
- `POST /rpc/v1/sources/{source_id}/scan`
  - 触发扫描任务，返回 `job_id`
- `POST /rpc/v1/sources/{source_id}/scan:fs-watch`
  - 文件变更触发扫描（支持去重复用已有 fs_watch 任务）
- `GET /rpc/v1/scan-jobs/{job_id}`
  - 查询扫描进度与结果
- `POST /rpc/v1/scan-jobs/{job_id}/cancel`
  - 请求取消扫描任务（pending 立即取消，running 异步停止）
- `POST /rpc/v1/scan-jobs/{job_id}/retry`
  - 失败/取消任务重试，创建新 `job_id`

任务系统接口（预留/已接入基础查询控制）：

- `GET /rpc/v1/task-jobs`
  - 任务列表（支持按 `job_type/status` 过滤）
- `GET /rpc/v1/task-jobs/{job_id}`
  - 任务详情
- `POST /rpc/v1/task-jobs/{job_id}/cancel`
  - 取消 pending/running 任务
- `POST /rpc/v1/task-jobs/{job_id}/retry`
  - 重试 failed/cancelled 任务（受重试上限约束）

### 5.3 照片

- `POST /rpc/v1/photos/search`
  - 条件分页查询（时间、名称、路径、相册、备注）
- `GET /rpc/v1/photos/{photo_id}`
  - 照片详情（含 EXIF、相册归属）
- `PATCH /rpc/v1/photos/{photo_id}/remark`
  - 更新照片备注
- `POST /rpc/v1/photos/batch/delete`
  - 批量删除（软删）
- `POST /rpc/v1/photos/batch/add-to-album`
  - 批量加入相册

`POST /rpc/v1/photos/search` 请求示例：

```json
{
  "keyword": "人才公园",
  "album_id": "alb_xxx",
  "start_time": "2020-01-01T00:00:00Z",
  "end_time": "2020-12-31T23:59:59Z",
  "page": 1,
  "page_size": 100,
  "order_by": "sort_time",
  "order": "desc"
}
```

### 5.4 相册

- `POST /rpc/v1/albums`
  - 创建相册：`{ name, remark }`
- `GET /rpc/v1/albums`
  - 相册分页列表（按创建时间倒序）
- `GET /rpc/v1/albums/{album_id}`
  - 相册详情（含照片分页）
- `PATCH /rpc/v1/albums/{album_id}`
  - 修改名称/备注
- `PATCH /rpc/v1/albums/{album_id}/cover`
  - 设置封面图
- `POST /rpc/v1/albums/{album_id}/photos:add`
  - 增加照片
- `POST /rpc/v1/albums/{album_id}/photos:remove`
  - 删除照片

## 6. 前端对接建议

- 照片栏：调用 `photos/search`，使用虚拟滚动 + 分页增量加载。
- 详情页：`photos/{id}` 一次取全。
- 批量操作：维护前端选中集，统一调用批量接口。
- 相册页：列表与详情分离，避免一次加载全部照片。

## 7. 里程碑建议（与需求优先级对齐）

### M1（P0）

- 数据源管理 + 扫描任务 + 入库
- 照片列表/详情 RPC
- 相册基础 CRUD + 关联关系
- 目录规则自动建相册（首条规则）

### M2（P1）

- 批量操作完善
- 索引优化与查询性能压测
- 相册封面/备注编辑体验完善

### M3（P2）

- 扩展特征管线接入（人脸/内容）
- 高级检索
- 非本地存储适配器接入

## 8. 风险与决策点

1. **数据库选型**：SQLite 在超大规模/高并发场景有限，需预留 PostgreSQL 迁移路径。
2. **EXIF 质量差异**：不同设备写入不一致，需容错解析和回退策略。
3. **目录规则复杂度**：建议以“规则注册表”方式逐步扩充，避免硬编码膨胀。
4. **删除策略**：V1 默认软删 + 可配置物理删，防止误删不可恢复。
